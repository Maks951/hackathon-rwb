Общие положения; сценарии; функциональные требования; модель данных; интеграции; нефункциональные требования; приемка.

## Ответственные лица и согласование
Дмитрий: Docker и тестирование. Ярослав: API и pipeline. Роман: хранилище и SQL. Владимир: Qwen. Владелец frontend и утверждающий требования уточняются командой. Документ не является подтверждением приемки.

## Термины и используемые документы
Run: задание генерации. Step: этап задания. Artifact: файл с размером и SHA256. Runtime: набор адаптеров. Исходники пяти регламентов находятся в docs/source-pdfs; API-контракт в contracts/platform-openapi.json. При расхождениях реализации с требованиями фиксируется открытый пункт, а не фиктивное согласование.

## Назначение, цель, условия и ограничения
Генерация приложения и документации из бизнес-текста. Парковка является одним из проверочных примеров. Платформа Python/Angular отделена от генерируемого продукта .NET/Angular/PostgreSQL. P0 рассчитан на закрытый командный доступ и один worker; JWT/RBAC и публичная многопользовательская эксплуатация не реализованы.

## Сценарии использования
UC-01: пользователь создает проект. Предусловие: API и БД доступны. Вводит имя (1–120 символов) и требования (20–50000), получает сохраненный проект. Некорректный ввод отклоняется, ошибка БД не считается успехом.
UC-02: пользователь запускает генерацию. API с Idempotency-Key создает queued run со snapshot требований. Worker получает running run, выполняет analyze/design, генерацию, проверки и до двух repair. UI опрашивает статус и события. Повтор ключа возвращает тот же run; другой активный run проекта вызывает 409. При ошибке модели, timeout или остановке worker сохраняется failed и диагностическая ошибка.
UC-03: пользователь скачивает продукт. Предусловия: validation passed, зарегистрирован package. Возвращается проверенный по SHA256 ZIP. До готовности возвращается 409. Скачивание ZIP само по себе не доказывает запуск продукта.

## Диаграмма последовательности
Пользователь → UI → POST project → PostgreSQL → POST run → queued.
Worker → SQL claim/commit → Qwen → validation runner → сохранение артефактов/ZIP.
UI → GET run/events → terminal status → GET download.
Диаграмма UML дана в platform-flow.mmd; внешние вызовы выполняются вне SQL-транзакции.

## Функциональные требования
FR-01: создание и чтение проектов. FR-02: идемпотентный запуск и хранение snapshot. FR-03: очередь, heartbeat, stale recovery. FR-04: генерация по единому SystemSpec/API-контракту. FR-05: реальные сборка, тесты, API/security проверки. FR-06: документация по регламентам и выдача проверенного ZIP. FR-07: отображение ошибок и прогресса.

## Frontend
Главная страница со списком и созданием проектов, страница проекта и страница запуска. UI обращается к /api/v1 через same-origin nginx proxy. Контракт camelCase, состояния queued/running/succeeded/failed. Polling прекращается на terminal status. Figma-макеты не предоставлены.

## Backend и модель данных
projects хранит имя и требования. runs содержит project_id, requirements_snapshot, idempotency_key, статусы, heartbeat, ошибку, package_path. steps хранит попытки, вход/выход и metadata. run_events хранит sequence внутри run. artifacts содержит путь, MIME, размер, SHA256 и принадлежность run/step. UUID/FK и уникальные ограничения определены SQLAlchemy и Alembic. Миграция head: 0006_worker_metadata.

## Интеграции
Внутренние: UI/API, API/PostgreSQL, worker/PostgreSQL, общий generated volume. Внешняя: Qwen API с конфигурацией окружения. ValidationRunner остается неподключенным. Publisher/deployer опциональны, адрес preview не выдумывается.

## Метрики и нефункциональные требования
Лимиты: 500 файлов, 1 MiB/файл, 24 MiB/дерево, 8 MiB/ответ модели; run timeout 900 секунд, heartbeat 10, stale 60 по умолчанию. Это настройки, а не измеренный SLA. Производительность, RTO/RPO, нагрузка и сроки хранения требуют согласования и измерений.
Надежность: короткие транзакции, восстановление stale как failed, сохранение данных в volumes. Масштабирование worker требует проверки на PostgreSQL. Сопровождение: stdout/stderr, история событий, отдельные миграции, документированный restart. Backup/restore и мониторинг VM пока не подтверждены.
Безопасность: path traversal/symlink проверки, manifest SHA256, секреты только в ENV; demo ограничена loopback. Удаленный доступ только через согласованный канал команды. Подключение TLS, RBAC, /metrics, централизованных логов и оповещений остается открытым требованием.

## Трассировка и критерии приемки
FR-01/02: tests/test_projects*, test_api, test_sql_worker. FR-03: SQL worker tests на SQLite; PostgreSQL race test не выполнен. FR-04: Qwen adapter/schema tests с подменой HTTP, живой Qwen не проверен. FR-05: открыто, нужен runner. FR-06: storage/documentation tests; полный результат не подтвержден. FR-07: 12 frontend tests и production build.
Приемка требует реального run с ID, успешных обязательных проверок, скачанного ZIP и запуска продукта по бизнес-сценарию. Сейчас этот критерий НЕ выполнен.
